TIER DESIGN

Reuse a destination pool across difficulty tiers

Let three item recipes select different rule sets over the same places. Decide deliberately whether players progress now or return in a new game.

1. Prepare data2. Configure3. Use the map4. Adapt it

Complete standalone TOML · example values, not a balance preset · no plugin rebuild required

01 / PREPARE THE GAME DATA

What to create or confirm

File / systemRequired work
CubeMainThree exact Red Portal recipes: tsc, r01 and r02.
Levels / statsGroups [2], [8, 9] and [21–25]; fire-resistance stat 39 in effective data.

Use the item, Level, stat and skill IDs from your effective mod data. The complete TOML below does not create TXT rows. If you change an input combination, update both CubeMain and its route.

02 / CONFIGURE THE MAP

The decisions in this configuration

  1. Connect recipes to tiers

    Each item selects tier1, tier2 or tier3. Tier names are identifiers; the ingredients are what players use to choose them.

  2. Repeat the pool under each tier

    All three tiers contain the same three Level groups. Adjust density and tier baselines while keeping the destination IDs aligned.

  3. Keep ranks consistent

    Ranks 1, 2 and 3 pair with monster fire-resistance baselines +0, +5 and +10. The rank rule validates tier monster baselines; it does not measure total difficulty.

# Complete example: three tiers reuse one Level pool across games.
# In one game, a selected group's Levels cannot be selected by ANY tier again.
# Define matching Red Portal recipes for tsc, r01, and r02 in CubeMain.
# Stat 39 and all Level IDs must match your effective mod data.
config_version = 1

[cube_routes.first]
inputs = ["tsc"]
tier = "tier1"

[cube_routes.second]
inputs = ["r01"]
tier = "tier2"

[cube_routes.third]
inputs = ["r02"]
tier = "tier3"

[tiers.tier1]
difficulty_rank = 1
trait_count = { min = 0, max = 0 }
base_stats = [{ stat_id = 39, target = "monster", value = 0 }]

[tiers.tier1.groups.field]
levels = [2]
entrances = [{ level = 2, weight = 1 }]
density = 100

[tiers.tier1.groups.underground]
levels = [8, 9]
entrances = [{ level = 8, weight = 1 }]
density = 100

[tiers.tier1.groups.five_levels]
levels = [21, 22, 23, 24, 25]
entrances = [{ level = 21, weight = 1 }]
density = 100

[tiers.tier2]
difficulty_rank = 2
trait_count = { min = 0, max = 0 }
base_stats = [{ stat_id = 39, target = "monster", value = 5 }]

[tiers.tier2.groups.field]
levels = [2]
entrances = [{ level = 2, weight = 1 }]
density = 150

[tiers.tier2.groups.underground]
levels = [8, 9]
entrances = [{ level = 8, weight = 1 }]
density = 150

[tiers.tier2.groups.five_levels]
levels = [21, 22, 23, 24, 25]
entrances = [{ level = 21, weight = 1 }]

[tiers.tier3]

03 / USE THE MAP

What the player should experience

Action / resultExpected behavior
Open tier1 and select [2]Level 2 becomes used globally.
Then open tier2Only [8, 9] and [21–25] remain eligible.
Then open tier3The remaining unused group can still be selected. A fresh game restores all candidates.

Use the recipe in a fresh game with the required ingredients, enter its portal, and open the automap. Check the tier, density and effect text against the result above. Syntax and rolls are checked against the configuration core; these steps are the in-game checks to perform in your own mod.

Design boundary. A new tier or group name does not create a new copy of a used Level. If every candidate overlaps the used set, the next-tier item cannot open another map in that game.

04 / ADAPT THE DESIGN

Change the behavior intentionally

Guarantee independent progression capacity
Give each tier disjoint Level groups instead. See the three-tier progression task.
Make more maps available per game
Add more disjoint groups to the pool. A larger weight does not add capacity.
Add a tier bonus
Add a fixed player baseline or monotonic monster baseline to the tier. Use group baselines for rolled values.

When merging this design into your existing TOML, copy its referenced traits and modifiers as well as the route and tier. Keep only one root configuration and HUD table, rename colliding identifiers consistently, and check Level overlap across every tier.
