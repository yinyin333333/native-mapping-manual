Reuse a destination pool across difficulty tiers

Let three item recipes select different rule sets over the same places. Recrafting overlapping Levels replaces the old tier map after everyone leaves.

1. Prepare data2. Configure3. Use the map4. Adapt it

What to create or confirm

File / systemRequired work
CubeMainThree exact Red Portal recipes: tsc, r01 and r02.
Levels / statsGroups [2], [8, 9] and [21–25]; fire-resistance stat 39 in effective data.

See how to find data IDs, CubeMain row syntax and HUD node installation.

Use the item, Level, stat and skill IDs from your effective mod data. The complete TOML below does not create TXT rows. If you change an input combination, update both CubeMain and its route.

The decisions in this configuration

  1. Connect recipes to tiers

    Each item selects tier1, tier2 or tier3. Tier names are identifiers; the ingredients are what players use to choose them.

  2. Repeat the pool under each tier

    All three tiers contain the same three Level groups. Adjust density and tier baselines while keeping the destination IDs aligned.

  3. Keep ranks consistent

    Ranks 1, 2 and 3 pair with monster fire-resistance baselines +0, +5 and +10. The rank rule validates tier monster baselines; it does not measure total difficulty.

# Complete example: three tiers reuse one Level pool in the same game.
# Every craft rolls all groups. Overlap replaces the whole old group after it is clear.
# Define matching Red Portal recipes for tsc, r01, and r02 in CubeMain.
# Stat 39 and all Level IDs must match your effective mod data.
config_version = 1

[cube_routes.first]
inputs = ["tsc"]
tier = "tier1"

[cube_routes.second]
inputs = ["r01"]
tier = "tier2"

[cube_routes.third]
inputs = ["r02"]
tier = "tier3"

[tiers.tier1]
difficulty_rank = 1
trait_count = { min = 0, max = 0 }
base_stats = [{ stat_id = 39, target = "monster", value = 0 }]

[tiers.tier1.groups.field]
levels = [2]
entrances = [{ level = 2, weight = 1 }]
density = 100

[tiers.tier1.groups.underground]
levels = [8, 9]
entrances = [{ level = 8, weight = 1 }]
density = 100

[tiers.tier1.groups.five_levels]
levels = [21, 22, 23, 24, 25]
entrances = [{ level = 21, weight = 1 }]
density = 100

[tiers.tier2]
difficulty_rank = 2
trait_count = { min = 0, max = 0 }
base_stats = [{ stat_id = 39, target = "monster", value = 5 }]

[tiers.tier2.groups.field]

[tiers.tier2.groups.underground]

What the player should experience

Action / resultExpected behavior
Open tier1 and select [2]The tier1 map at Level 2 becomes active.
Then open tier2All three groups remain candidates. If [2] is selected, the old tier1 group is replaced after it is clear; a non-overlapping selection leaves that map active.
Then open tier3Again roll all three groups. Any overlapping old groups are replaced in full; the others remain active.

Use the recipe with the required ingredients, enter its portal, and open the automap. Before repeating a craft, recover needed items and player corpses and move all players and allies out of every Level in the replacement area; rooms must no longer be in use. See the repeat-craft procedure. Check the tier, density and effect text against the result above. Syntax and rolls are checked against the configuration core; these steps are the in-game checks to perform in your own mod.

Design boundary. Tier names do not create independent Level instances. Reusing a Level replaces the overlapping old group, so recover items and corpses and clear every affected floor before recrafting.

Change the behavior intentionally

Keep tier maps active together
Give each tier disjoint Level groups so moving to another tier does not retire the previous map. See the three-tier progression example.
Add more simultaneous destinations
Add disjoint groups to the pool. Weight changes selection probability; repeatedly selecting the same group replaces its current map rather than creating another instance.
Add a tier bonus
Add a fixed player baseline or monotonic monster baseline to the tier. Use group baselines for rolled values.

When merging this design into your existing TOML, copy its referenced traits and modifiers as well as the route and tier. Keep only one root configuration and HUD table, rename colliding identifiers consistently, and check Level overlap across every tier to understand which entire groups will be replaced.
