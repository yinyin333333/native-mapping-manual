01 / OVERVIEW

Native Mapping
Configuration manual.

Turn a CubeMain Red Portal recipe into a map with a selected tier, destination, monster density, and temporary effects.

Native Mapping adds configurable rules to existing game Levels. This manual explains the plugin’s capabilities, its configuration structure and map lifecycle, then shows how to install it and combine those features in complete examples.

GAME DATA

What exists in the world

Item codes, Cube recipes, terrain, monster composition, stat and skill definitions, ordinary loot, and Treasure Class contents.

CubeMain · Levels · MonStats · ItemStatCost · Skills · TreasureClassEx

PLUGIN CONFIGURATION

What this map selects

The route, tier, weighted Level group, entrance, density, stat rolls, traits, optional monster aura, and supplemental TC.

native-mapping.toml

What the plugin does not add: independent copies of a Level, monster respawning, a new monster pool system, map-clear rewards, portal-use limits, or player transformations.

02

CAPABILITIES & INTERNAL MODEL

How the mapping system is organized

The plugin has two connected parts: a configuration describes possible maps, and an active-map record holds the result selected for a particular game. Recipes choose configurations; players and monsters receive effects according to the Levels belonging to the active result.

What the plugin controls

CapabilityWhat you can defineWhere to configure it
Entry recipesSeveral exact ingredient combinations can select the same tier or different tiers. A route can also apply modifiers.cube_routes + real CubeMain recipes
DestinationsWeighted groups of existing Levels, each with one or more weighted portal entrances.tiers.*.groups
Map difficulty and bonusesMonster density, fixed tier stats, fixed or rolled group stats, weighted random traits and one optional monster aura.density, base_stats, traits
Recipe-specific variationsForce traits, replace or extend their candidate pool, or change the total trait count without duplicating a tier.modifiers
Player effectsTemporary bonuses or penalties for each player in an active map. The same map rules apply to party members in its Levels.Stats with target = "player"
Additional rewardsOne supplemental TC per tier, called after an eligible monster’s ordinary drop. The TC can contain items and child TCs.progression + TreasureClassEx
Map informationTier, density, baseline descriptions and selected trait descriptions on the automap HUD.hud, effect text and both UI layouts
Multiplayer consistencyHost-owned results and gameplay effects, with map-result synchronization to Join clients.Matching runtime configuration and effective game data

The configuration objects and their relationships

ObjectIts roleWhat its name does not do
RouteConnects an exact compiled Cube recipe to a tier and an ordered modifier list.A route name does not create an item or recipe.
TierA reusable rule set containing fixed baselines, default trait count, groups and an optional reward TC.Calling it tier3 does not automatically scale any values.
GroupOne candidate map: effect-area Levels, entrance candidates, density and local effect policy.A group name does not generate terrain or an instance.
TraitOne selectable package containing player stats, monster stats, an aura, or a combination.Several stats inside a trait do not consume several trait slots.
ModifierA reusable recipe option that changes the pool, forced traits or total count.The plugin does not infer modifiers from extra ingredients; a matching route must name them.

How a configuration becomes an active map

  1. Load configuration.

    The loader reads the runtime TOML when the plugin loads. The parser resolves named references and validates the configuration. Existing runtime files remain in place across DLL updates.

  2. Match the Cube recipe.

    CubeMain owns recipe matching and conditions. For an exact Red Portal recipe, the plugin identifies the corresponding route by item codes and quantities.

  3. Resolve a candidate.

    Exclude every group that overlaps the game’s used Levels. Select a group, entrance and density; resolve baseline values, modifiers and traits. The resulting values belong to this map.

  4. Activate after portal creation.

    A successfully created portal pair commits the map. All its Levels become used for the game, including floors nobody has visited.

  5. Apply rules by location.

    Players in those Levels receive its player stats; the Host applies the map’s monster-side rules and supplemental drops. Other non-overlapping maps can remain active at the same time.

  6. Leave, return or end the game.

    Player effects follow each player’s map membership. Returning preserves the map result without stacking bonuses or respawning monsters. Ending the game clears the active maps and used-Level set.

A resolved map is shared world state. It is not a private effect attached to the item user. Entering an active Level through an ordinary connection still enters that map’s effect area. A Host going to town does not remove effects from a Join who remains inside.

Which values are guaranteed and which are selected?

Configuration layerWhen it contributesHow to use it
Tier baselineEvery result of that tier; fixed stat values only.Common tier difficulty or a guaranteed player bonus.
Group baselineEvery result of that group; fixed or rolled values.A destination-specific effect or penalty.
Selected traitsThe forced traits plus the weighted random selection, within the final total count.Variation between maps, or inseparable challenge/reward packages.
DensityThe selected group’s fixed or rolled percentage.Scale its underlying monster density; this is not a stat entry or trait slot.

Stat entries with the same target, stat ID and layer are added together. For example, player MF +25 from the tier and +75 from a selected trait produce +100. Group settings do not simply overwrite tier baselines.

03

MAP STRUCTURE

A tier is a rule set. A Level is a place.

Tier
A reusable configuration of fixed base stats, trait count, optional progression TC, and map groups. A recipe selects it by ID.
Group
A candidate map inside a tier. Its levels define the effect area; its weight determines selection among eligible groups.
Level
A numeric ID from the game's effective Level data. Naming a group field does not change the terrain behind its IDs.
Entrance
A possible portal destination inside the selected group's Levels. Multiple entrances have their own weights.

Several Levels can belong to one map

Excerpt · multi-level.toml
Complete file ↓
[tiers.tier1.groups.five_levels]
weight = 100
levels = [21, 22, 23, 24, 25]
entrances = [{ level = 21, weight = 100 }]
density = 150
trait_pool = []

Group weights and entrance weights are separate

In this example, the first roll chooses field or underground. Only after choosing field does the game-facing map result choose between entrances 2 and 3.

Weighted selection while both groups are unused · download the complete example

field702, 32: 3 · 3: 1Level 2: 52.5%
Level 3: 17.5%
underground308, 98: 100Level 8: 30%

The 52.5% is 70 / 100 × 3 / 4. After a group is excluded, the remaining group weights are normalized again. An entrance weight never changes the chance of selecting its parent group.

Reuse the same destinations at different tiers

The same Level pool can be declared under several tiers. The chosen tier supplies its own baseline, density and trait policy. This does not create separate instances of those Levels.

These are illustrative values, not a balance recommendation. Add other appropriate monster or player stats as needed. The next section explains why a group used at tier1 is unavailable at tier2 in that same game.

04

THE SAME-GAME RULE

A used Level stays used.

When a portal successfully activates a map, every Level in its selected group is marked used for that game—even floors nobody has visited. A later group is excluded if it overlaps by even one Level, regardless of tier.

  • All candidates used: the route is refused before ordinary Cube execution consumes the ingredients. The game gives its native unavailable feedback.
  • Leave and return: an existing map keeps its resolved result. Returning through its portal does not reroll effects or respawn monsters.
  • Start a new game: active maps and the used-Level set reset.
  • Advance now or later: a next-tier item can be used in the same game if that tier still has an eligible group, or saved for a new game.

Map membership follows the active map's Level set, not which portal a particular player used. Entering the same active Level by an ordinary connection still enters its mapping effect area.

05

EXACT INPUTS & REUSABLE TRAITS

Give each recipe a clear purpose.

CubeMain first matches its normal recipe. The plugin then matches the compiled recipe's exact item codes and quantities to a cube_routes entry. Order does not matter; duplicates and additional required inputs do.

For a route with inputs = ["tsc", "r01"]
Recipe's exact inputsRoute matchReason
tsc + r01YesExact pair
r01 + tscYesOrder is irrelevant
tscNoMissing required input
tsc + r01 + r01NoDifferent quantity; needs its own route

For two copies, write the code twice: inputs = ["tsc", "tsc"]. Use exact item-code descriptors, not broad item type/family inputs. Keep op, param, and value for their ordinary CubeMain meanings. They are not route markers.

Three recipes can select the same tier

Excerpt · recipe-modifiers.toml
Complete file ↓
[cube_routes.plain]
inputs = ["tsc"]
tier = "tier1"

[cube_routes.aura]
inputs = ["tsc", "r01"]
tier = "tier1"
modifiers = ["force_conviction"]

[cube_routes.speed]
inputs = ["tsc", "r02"]
tier = "tier1"
modifiers = ["speed_only"]

Route IDs, tier IDs, and modifier IDs do not need to be identical. Each reference must point to the table it names. None of these item codes is reserved by the plugin.

Excerpt · modifiers used above
[modifiers.force_conviction]
forced_traits = ["conviction"]

[modifiers.speed_only]
trait_pool_mode = "replace"
trait_pool = ["monster_attack", "monster_move", "monster_cast"]
trait_count = { min = 3, max = 3 }
  • forced_traits occupy the final count first and are removed from the random candidates. They do not add free slots.
  • extend adds candidates; replace replaces the current pool. Multiple modifiers run in the route's listed order.
  • Count precedence is modifier → group → tier. Two modifiers with conflicting counts are rejected; the last one does not silently win.
  • The maximum count must fit the distinct forced and random candidates. If forced traits exceed the minimum, the effective minimum rises to their count.
06

MAP EFFECTS

Control the baseline and the variation.

Density is already a randomizable group setting

density = 150 means 150% of the Level's original monster density. A range such as { min = 125, max = 200, step = 25 } selects 125, 150, 175, or 200 once for the resolved map.

100%Original density
150%1.5 × original
200%2 × original

The allowed multiplier is 1–1000%. Original density zero stays zero. The game's population path caps the resulting MonDen at 10,000. Density changes do not regenerate already-populated rooms.

Three stat sources add together

SourceApplies whenValue form
Tier base_statsEvery group selected from the tierFixed only
Group base_statsThis group is selectedFixed or range
Trait statsThis trait is selectedFixed or range

stat_id identifies the actual ItemStatCost stat. The optional stat name is descriptive. target is player or monster, with player as the default; layer defaults to 0. There is no separate stat manifest.

Write integer values in the stat's game-facing units. The plugin handles ItemStatCost ValShift. A valid ID is not a promise that every stat is meaningful for every monster or player context.

Share a roll within one stat array

Excerpt · attack-speed trait in recipe-modifiers.toml
[traits.monster_attack]
weight = 100
text = "Monster Attack Speed {signed0}%"
stats = [
  { stat_id = 68, target = "monster", value = { min = 10, max = 30, step = 5 }, roll_group = "speed" },
  { stat_id = 69, target = "monster", value = { min = 10, max = 30, step = 5 }, roll_group = "speed" }
]

Both entries receive the same selected number. A shared roll_group must use an identical range in that array. The same name in another trait, a tier baseline, or a group baseline does not share this roll.

Use ranks to check fixed monster baselines

If one tier declares difficulty_rank, every tier must declare a unique rank. The parser checks non-negative, non-decreasing tier monster baseline totals for each stat/layer. An omitted stat counts as zero. Player bonuses, group effects, random traits, density, and rewards are outside that comparison; rank alone does not create difficulty.

Add a monster aura through a trait

Excerpt · recipe-modifiers.toml
[traits.conviction]
weight = 50
text = "Monster Aura: Conviction Lv.{value0}"
monster_aura = { skill_id = 123, level = 10 }

An aura can use a fixed or ranged level from 1–99. A resolved map permits one monster aura. Keep the pool and forced traits from selecting two aura traits together. An aura trait can also contain stats; its first display value is the aura level, followed by its stat values.

In the current implementation, a monster already using the same right-skill ID keeps that existing skill; the plugin does not force its level to match the TOML in that branch. No player transformation or arbitrary state setting is provided.

07

SUPPLEMENTAL DROPS

The normal drop finishes.
Then the extra TC is called.

A tier can name one supplemental Treasure Class. On the Host, an eligible monster drop in that active map runs its ordinary drop path first, then calls the configured TC once. The contents and probabilities remain in TreasureClassEx.txt.

Excerpt · tier-progression.toml
Complete file ↓
[tiers.tier2.progression]
treasure_class = "Mapping_Tier2"
trigger = "all_monsters"

Start with one dedicated TC per tier

For progression items, a simple layout is easiest to maintain. Create the named rows and items in TXT, then reference the rows from the appropriate tiers.

Selected TreasureClassEx fields only · these are not complete replacement TXT rows
Treasure ClassPicksNoDropItem1Prob1Purpose
Mapping_Tier1199nm21Next-tier item from tier1
Mapping_Tier2199nm31Next-tier item from tier2

Before player-count adjustment, 1 / (99 + 1) is a 1% item weight per pick. Actual NoDrop is affected by game rules including player count. This is not a fixed multiplayer drop-rate guarantee.

One direct TC can contain several child TCs

The single TOML slot does not limit the TC to one possible reward. A root can contain item codes and child TCs in its Item/Prob entries. Each chosen child uses its own TC rules.

A tier restricts the extra call, not the TC everywhere

Where the TC is referencedInside its active tier mapOutside that map
Only the tier's progression entrySupplemental call runsNo supplemental call
Also inside an ordinary parent TCBoth ordinary and supplemental paths can reach itThe ordinary parent can still reach it
As a child of a progression-only parentIts parent can select itNo call through that isolated progression path

For a tier-only reward, keep its TC out of ordinary drop trees. Putting it under an ordinary parent TC does not add a tier restriction. The plugin never globally disables that TC.

  • Trigger: only all_monsters is supported in this build. There is no boss-only selector, chest trigger, or map-clear trigger.
  • Location: the dead monster's Level and the active map determine the tier. The Host's current HUD location does not select the drop TC.
  • Duplicates: the guard prevents a repeat supplemental call for the same tracked death. It does not deduplicate rewards already selected by the ordinary TC.
  • TC lookup: names bind to effective game data. A loose active-mod TXT takes precedence when available; packaged data uses the compiled linker. Missing, duplicate, or unresolved names do not produce a supplemental call.
  • Defaults: progression is disabled in the shipped default TOML. Add a progression table only after defining the real TC. No progression tables means no supplemental death/drop hook.
08

DISPLAY & MULTIPLAYER

One map result, shared by the party.

HOST

Owns gameplay decisions

Chooses the destination and map result. Applies authoritative player and monster stats, density, auras, and supplemental drops.

JOIN

Mirrors the resolved map

Replays the received route and seed against local configuration and checks the result fingerprint. Displays the map and local player stats; it does not make a second supplemental drop roll.

Use matching plugin versions, runtime TOML, and effective mod data on Host and Join. Mismatched routes or resolved results are rejected. The plugin network service is for local/TCP-IP games, not Battle.net.

Effect cleanup follows the individual player's destination. A Host leaving a map does not remove the bonuses of a Join who stays there. A player arriving at a map with no player stats loses the old map's effects. Host snapshot identity and local lifecycle identity are kept separate.

What the HUD displays

  1. The tier ID.
  2. The density line.
  3. Tier and group baseline entries with a text field.
  4. The selected traits, using each trait's text.
TokenMeaningExample use
{tier}, {id}Tier or current entry IDIdentify the source in a line
{density}Resolved density percentageDensity: {density}%
{value}, {value0}First valueConviction Lv.{value0}
{signed}, {signed0}First value with a signMagic Find {signed}%
{value1}, {signed1} …Subsequent values, in orderSeveral stat values in one trait

The mapping HUD is visible with the automap. Position and overall color come from MappingInfoText in both layout files. The TOML color fields are parsed, but the current builder does not emit per-line color markers.

max_lines limits display, not effects. The final line becomes overflow_text when needed; at max_lines = 2, only tier and density remain. A hidden baseline still applies even if it has no text.

09

GETTING STARTED

Install once. Edit the runtime TOML.

Use a Native Mapping DLL built for your D2RLoader/game build. Close the game before replacing plugin files. A configuration edit does not require recompiling the plugin.

  1. Place the DLL in the loader's active scope

    <scope> is the scope root used by your loader setup. It is a placeholder, not a literal folder name.

    Plugin location
    <scope>/d2rloader/plugins/NativeMapping.dll

  2. Merge the mapping HUD into both layouts

    Under the active mod's data root, update global/ui/layouts/hudwarnings.json and global/ui/layouts/hudwarningshd.json. Use the package layouts when there are no existing customizations; otherwise merge the mapping nodes.

    MappingInfoTextWrapper
    └─ MappingInfoText    Keep these names exact in both files.

    Both files place the mapping wrapper alongside the existing warning text, after TerrorZoneInfoTextWrapper. A missing layout affects the display; it does not define the map's effects.

  3. Edit the file the loader creates

    On first load, the loader creates the missing configuration from the DLL's embedded defaults. Fully close the game, then edit:

    The runtime file
    <scope>/d2rloader/config/native-mapping.toml

    An existing TOML is preserved when you update the DLL. Editing a source-tree plugin/native-mapping.toml only changes future embedded defaults after a rebuild.

  4. Restart after changes

    The plugin reads configuration at load time. Restart the game and loader after editing it. Update your mod's effective TXT/compiled data as required by your normal mod workflow.

Building from source

From the plugin source root, use CMake 3.28+, Visual Studio 2022 with C++20/x64, Git, and a compatible PluginSDK. Replace <sdk-root> with your SDK directory.

PowerShell · developer setup
cmake -S . -B out -G "Visual Studio 17 2022" -A x64 -DD2RL_PLUGIN_SDK_DIR="<sdk-root>"
cmake --build out --config Release --parallel

The chosen build directory contains bin/NativeMapping.dll and package/. Building does not install the package. Use the output of your actual build directory; old output folders can contain older DLLs.

THE SMALLEST COMPLETE CONFIGURATION

One recipe. One group. One entrance.

Create an exact tsc input recipe with a Red Portal output in CubeMain.txt. The TOML below connects that matched recipe to Level 2 at the original density, with no traits or stat bonuses.

Before using an example: confirm the item codes, Level IDs, stat IDs, and skill IDs in your effective mod data. These are teaching configurations, not the plugin's shipped defaults. TOML does not create their required TXT rows.

# Level IDs are examples; confirm them against your mod's Levels.txt.
config_version = 1
enabled = true
random_salt = "mapping-example"

[hud]
enabled = true
density_text = "Monster Density: {value}%"
overflow_text = "+{value} more"
max_lines = 16

[cube_routes.scroll_map]
inputs = ["tsc"]

[tiers.tier1]
trait_count = { min = 0, max = 0 }

[tiers.tier1.groups.field]
weight = 100

01

Match the recipe

inputs contains its exact item codes and quantities.

02

Select a template

03

Define the map's extent

levels contains every Level belonging to the map. entrances chooses where the portal lands.

EXPECTED HUD TEXTtier1
Monster Density: 100%

Back up the runtime TOML and replace its contents with the complete file, rather than appending duplicate tables. Enter the game, use the recipe, travel through the portal, and open the automap to see the HUD. With only one group available, another attempt in the same game has no unused candidate.

How to edit this structure

  1. Choose the entry recipe. Use its exact item codes and quantities in a route. Point that route to your tier ID.
  2. Choose the area. Put every Level that should share the result in one group. Pick its actual portal landing from that same set.
  3. Separate guaranteed and selected effects. Tier baselines are fixed; group baselines can roll; traits are selected from a pool. Effects that must arrive together belong in one trait.
  4. Wire up dependencies. Every named tier, trait and modifier must exist. TC, item, stat and skill definitions belong to effective game data.
  5. Restart and check one change. Use a fresh game when reusing a destination. Compare the HUD and behavior with your intended map, then add the next feature.

CONFIGURATION V1

Field reference.

Names are configuration identifiers, not file paths. Numeric IDs refer to effective mod data. Integer ranges use { min, max, step }: step must be positive, min must not exceed max, and the interval must divide evenly by step.

Location / fieldsDefault and accepted values
Rootconfig_version = 1; enabled = true; random_salt = "native-mapping" (1–256 bytes). The salt influences map selection, not item generation seeds.
cube_routes.<id>inputs: 1–255 item codes, each 1–4 printable non-space bytes. tier: existing tier ID. modifiers: ordered IDs, default empty. Duplicate exact multisets, including compiled aliases, are rejected.
tiers.<id>base_stats: fixed values only, default empty. trait_count: { min, max }, defaults to zero. At least one group is required; every tier must be referenced by a route.
difficulty_rankOptional unsigned 32-bit rank. If used, required and unique on every tier. Ranked monster baseline totals must be non-negative and non-decreasing.
groups.<id>levels: unique IDs, 0–255, non-empty. entrances: non-empty { level, weight } entries, unique and inside levels. The numeric range alone does not establish a usable destination.
Group / entrance weightPositive unsigned 32-bit integer, default 1. Relative to the remaining eligible candidates.
Group densityInteger or range, 1–1000; default 100. A percentage of original density.
Group effect fieldsbase_stats allows fixed or ranged values. trait_pool is a list of distinct existing trait IDs. trait_count overrides the tier when present.
traits.<id>weight defaults to 1 and is positive. text defaults to the trait ID. Requires stats, monster_aura, or both.
A stat entrystat_id: required, 0–65535. stat: optional name. layer: 0–65535, default 0. target: player or monster, default player. value: signed 32-bit integer or range, default 0; native encoding limits also apply.
Stat display / sharingroll_group shares an identical range within one array. text defaults to empty for baseline entries. Optional color is parsed but not emitted as a line color.
monster_auraskill_id: required, 1–65535. skill: optional name. level: integer or range, 1–99, default 1. One aura per resolved map.
modifiers.<id>forced_traits, trait_pool, trait_count. Pool mode defaults to extend; explicit trait_pool_mode requires an explicit pool. Count conflicts in a route are rejected.
tiers.<id>.progressionOptional. One treasure_class name (1–63 printable bytes); trigger = "all_monsters". The real TC must resolve in effective data.
hudenabled=true; density_text="Monster Density: {value}%"; overflow_text="+{value} more"; max_lines=16 (2–256). tier_color, density_color, and trait_color do not set visible per-line colors in this builder.
diagnosticsenabled=false. Opt-in buffered diagnostic log; see troubleshooting.
diagnostic_hookshud=true, unit_room=true, other=true. Developer fault-isolation switches; keep all true for normal operation.

Identifiers accept letters, digits, underscores, hyphens and dots, up to 96 bytes. Quote literal dotted keys in TOML. Display text is single-line and limited to 256 bytes. A resolved map supports up to 256 stat entries before coalescing; the active map capacity is 64. These bounds do not define how many monsters a Level can contain.

WHEN THE RESULT IS UNEXPECTED

Check the rule that owns the result.

The recipe works, but the destination is unchanged.
Match the exact compiled recipe inputs and quantities to the route. Type/family descriptors do not qualify. Confirm that the recipe has a Red Portal output and the runtime TOML is the file being edited.
A tier stops opening after another map was used.
Check all candidate groups for shared Level IDs, even across tiers. One overlap excludes the entire group. Leaving the area does not reset the used set; leaving the game does.
The next-tier item does not drop.
The shipped defaults leave progression off. Add the tier's progression table, define the exact TC name and actual item in TXT, and check the TC's own NoDrop/Picks/Prob. Being in an ordinary Level with the same TC name is not an activation rule.
A tier-only reward appears outside the map.
Follow references from ordinary parent TCs. The plugin restricts its additional call, not every use of the named TC in game data.
A forced trait reduces the number of random traits.
Forced traits occupy the total count. For three random traits plus one forced trait, set the final count to four and supply enough remaining candidates.
Several stats roll different values.
Use the same roll_group and identical value ranges within the same array. A repeated roll_group name in different arrays does not share a roll.
The HUD is missing, but the map works.
Open the automap, enable the HUD, and confirm both layouts contain MappingInfoTextWrapper and MappingInfoText. Baselines need their own text to appear. The line limit can hide text without removing an effect.
An updated DLL still uses the old configuration.
Existing runtime TOML files are intentionally preserved. Edit that file explicitly and restart; the embedded default is not an automatic migration.
Host and Join show different map behavior.
Match the plugin version, actual runtime TOML, and effective mod data. A client must be able to reproduce the Host's route and result. Do not use different item/stat/skill/TC definitions on each side.
Reading an opt-in diagnostic log

Set [diagnostics] with enabled = true in the runtime TOML and restart. Read d2rloader/logs/native-mapping-diagnostic.log under the loader's log location.

Useful records include CONFIG_ACCEPT, CUBE_ROUTE_MATCH, CUBE_ROLL_REJECT, and PROGRESSION_TC_INVOKE. Output is buffered and flushed at lifecycle boundaries such as game entry and exit; the file need not update on every action. Return diagnostics to false for ordinary use.
