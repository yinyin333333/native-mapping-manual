PLUGIN CONFIGURATION

What this map selects

The route, tier, weighted Level group, entrance, density, per-Level monster pools, an optional random SuperUnique, stat rolls, traits, optional monster aura, and optional tier-based TC replacements.

native-mapping.toml · companion monstats.txt / superuniques.txt

What the plugin does not add: independent simultaneous copies of a Level, a fresh terrain seed on every craft, map-clear rewards, or player transformations. Recrafting can regenerate rooms and hunting content; it does not restart the whole game.

02

How the mapping system is organized

The plugin has two connected parts: a configuration describes possible maps, and an active-map record holds the result selected for a particular game. Recipes choose configurations; players and monsters receive effects according to the Levels belonging to the active result.

How a configuration becomes an active map

  1. Load configuration.

    The loader reads the runtime TOML when the plugin loads. The parser resolves named references and validates the configuration. Existing runtime files remain in place across DLL updates.

  2. Match the Cube recipe.

    CubeMain owns recipe matching and conditions. For an exact Red Portal recipe, the plugin identifies the corresponding route by item codes and quantities.

  3. Resolve a candidate.

    Select from all configured groups by weight on every craft, including previously selected Levels. Resolve the entrance, density, baselines, modifiers and traits. Prior use does not change the group probabilities.

  4. Prepare and replace.

    Find every existing map group touched by the selected Levels, including indirect overlaps. Require the whole replacement area to be clear of players, player corpses and allies, with rooms no longer in use. Retire those maps and clear their old portals and hunting content.

  5. Generate with the new result.

    The new density, configured monster pools, monster stats and aura are prepared before the first monster population. Each new map also gets a fresh chance to include its configured SuperUnique. The native portal/room path regenerates the area and commits the new map result. Non-overlapping active maps remain.

  6. Apply rules by location.

    Players in those Levels receive its player stats; the Host applies the map’s monster-side rules and TC replacements. Other non-overlapping maps can remain active at the same time.

  7. Leave, return or end the game.

    Player effects follow each player’s map membership. Re-entry without a new craft preserves the result and kill state. A new craft can replace the area; ending the game clears active map records.

A resolved map is shared world state. It is not a private effect attached to the item user. Entering an active Level through an ordinary connection still enters that map’s effect area. A Host going to town does not remove effects from a Join who remains inside.

Which values are guaranteed and which are selected?

Configuration layerWhen it contributesHow to use it

Stat entries with the same target, stat ID and layer are added together. For example, player MF +25 from the tier and +75 from a selected trait produce +100. Group settings do not simply overwrite tier baselines.

03

A tier is a rule set. A Level is a place.

Tier
A reusable configuration of fixed base stats, trait count, map groups, and an ID used by optional TC rules. A recipe selects it by ID.
Group
A candidate map inside a tier. Its levels define the effect area; its weight determines selection among all configured groups.
Level
A numeric ID from the game's effective Level data. Naming a group field does not change the terrain behind its IDs.
Entrance
A possible portal destination inside the selected group's Levels. Multiple entrances have their own weights.

Several Levels can belong to one map

Excerpt · multi-level.toml
Complete file ↓
[tiers.tier1.groups.five_levels]
weight = 100
levels = [21, 22, 23, 24, 25]
entrances = [{ level = 21, weight = 100 }]
density = 150
trait_pool = []

Group weights and entrance weights are separate

In this example, the first roll chooses field or underground. Only after choosing field does the game-facing map result choose between entrances 2 and 3.

04

Recraft a map to regenerate its area.

Every craft rolls from all groups in the chosen tier. The same Level can be selected again in the same game, even when the tier has only one group. If the selection overlaps an active map, the plugin replaces that entire existing group, including its unvisited floors. The area to clear starts with the selected Levels and expands to whole overlapping groups.

Before crafting another map

  1. Recover what you need. Pick up wanted floor items and recover player corpses in the entire old group. Remaining floor items will be removed.
  2. Leave every affected Level. All players and allies, including mercenaries and summons, must leave the whole replacement area. In the example, leaving only 140 is not enough if someone remains in 138 or 139.
  3. Let the rooms become inactive. Rooms still in use prevent regeneration. The preflight also checks the native ownership conditions needed to clear the area; leaving the visible floor alone is not a guarantee that every room is ready.
  4. Use the recipe again. The same recipe or a different tier can select overlapping Levels. A successful replacement removes the old portal pair and opens the new map using its freshly resolved effects.

Precondition refusal is not candidate filtering. A player, player corpse, ally or room still in use causes refusal before the original Cube operation. Ingredients are not passed to that operation on this path. The next attempt still rolls from all configured groups; it does not skip previously used or occupied destinations.

What is regenerated, and what stays?

Replaced in the affected areaPreserved
Old portal pair, remaining monsters, floor items, inactive saved unit records and prior population history.Level IDs, existing terrain settings and the game/Act seed. This is not a new independent instance or a new random terrain seed.
Rooms and hunting content through the native generation path; the new map’s density, configured monster pools, monster stats and aura apply from its first monster generation.Other active maps that do not overlap the replacement area.
The retired map’s effects, HUD state and TC replacements; the new result uses a new generation, so a configured SuperUnique can appear again.Game-wide quests and D2RCore event/Herald progress. Quest-dependent bosses, events and rewards do not all restart as if a new game had begun.

Walking back through an existing portal is not recrafting. Without a new craft, the map keeps its effects and kill state; re-entry does not replenish monsters or stack player bonuses. Ordinary travel into an active Level also enters that map’s effect area.

A configured SuperUnique belongs to that generation. Recrafting the same cow Level at the same tier allows its boss to appear again. At chance = 100, the new map gets another boss; lower percentages get a new chance. Re-entering the existing map, reloading its rooms or killing the boss does not trigger another spawn. See random SuperUnique placement.

Collect wanted items before recrafting. If a new portal fails to appear after replacement has started, the old portal, remaining monsters and floor items may already be gone. Do not rely on the previous map being restored or on automatic refunds of consumed ingredients. Pick up wanted items and recover player corpses before using the recipe again.

05

Give each recipe a clear purpose.

CubeMain first matches its normal recipe. The plugin then matches the compiled recipe's exact item codes and quantities to a cube_routes entry. Order does not matter; duplicates and additional required inputs do.

For a route with inputs = ["tsc", "r01"]
Recipe's exact inputsRoute matchReason
tsc + r01YesExact pair
r01 + tscYesOrder is irrelevant
tscNoMissing required input
tsc + r01 + r01NoDifferent quantity; needs its own route

For two copies, write the code twice: inputs = ["tsc", "tsc"]. Use exact item-code descriptors, not broad item type/family inputs. Keep op, param, and value for their ordinary CubeMain meanings. They are not route markers.

Three recipes can select the same tier

Excerpt · recipe-modifiers.toml
Complete file ↓
[cube_routes.plain]
inputs = ["tsc"]
tier = "tier1"

[cube_routes.aura]
inputs = ["tsc", "r01"]
tier = "tier1"
modifiers = ["force_conviction"]

[cube_routes.speed]
inputs = ["tsc", "r02"]
tier = "tier1"
modifiers = ["speed_only"]

Route IDs, tier IDs, and modifier IDs do not need to be identical. Each reference must point to the table it names. None of these item codes is reserved by the plugin.

Excerpt · modifiers used above
[modifiers.force_conviction]
forced_traits = ["conviction"]

[modifiers.speed_only]
trait_pool_mode = "replace"
trait_pool = ["monster_attack", "monster_move", "monster_cast"]
trait_count = { min = 3, max = 3 }
  • forced_traits can be declared on a group or supplied by a modifier. They occupy the final trait_count first, are removed from the random candidates, and do not add free slots. For example, a count of 2–11 with one forced group trait means one guaranteed trait plus 1–10 random traits.
  • extend adds candidates; replace replaces the current pool. Multiple modifiers run in the route's listed order.
  • Count precedence is modifier → group → tier. Two modifiers with conflicting counts are rejected; the last one does not silently win.
  • The maximum count must fit the distinct forced and random candidates. If forced traits exceed the minimum, the effective minimum rises to their count.
06

Control the baseline and the variation.

Density is already a randomizable group setting

density = 150 means 150% of the Level's original monster density. A range such as { min = 125, max = 200, step = 25 } selects 125, 150, 175, or 200 once for the resolved map.

The parser accepts any positive TOML integer that fits signed 64-bit storage; there is no 1000% parser ceiling. For example, density = 2000 means 2000% (20×) of the Level's original density. Original density zero stays zero. The game's population path caps the resulting MonDen at 10,000, so very large percentages can reach the same native cap. Changing TOML alone does not update an existing populated map. A new craft performs regeneration, with the new density, monster stats and aura available during the first population.

Three stat sources add together

SourceApplies whenValue form
Tier base_statsEvery group selected from the tierFixed only
Group base_statsThis group is selectedFixed or range
Trait statsThis trait is selectedFixed or range

stat_id identifies the actual ItemStatCost stat. The optional stat name is descriptive. target is player or monster, with player as the default; layer defaults to 0; see parameterized stats below.

Use values appropriate to the chosen stat. For example, All Skills uses skill levels, while maximum mana uses a percentage. A monster effect also depends on the attacks or skills that monster uses.

Share a roll within one stat array

Excerpt · attack-speed trait in recipe-modifiers.toml
[traits.monster_attack]
weight = 100
text = "Monster Attack Speed {signed0}%"
stats = [
  { stat_id = 68, target = "monster", value = { min = 10, max = 30, step = 5 }, roll_group = "speed" },
  { stat_id = 69, target = "monster", value = { min = 10, max = 30, step = 5 }, roll_group = "speed" }
]

Both entries receive the same selected number. A shared roll_group must use an identical range in that array. The same name in another trait, a tier baseline, or a group baseline does not share this roll.

Use layer for a stat’s parameter, not its strength

A stat entry is identified by (target, stat_id, layer). value is the amount; layer is the parameter that distinguishes entries of a parameterized stat. Ordinary Magic Find or resistance entries use layer 0. A Level ID, tier number or desired bonus amount does not belong in this field.

EntryStat identityParameter / amount
Magic Findstat_id = 80layer = 0, value = 25: a +25 bonus.
Single-skill bonus, reference datastat_id = 107 (item_singleskill)The layer identifies the skill; value is the skill-level bonus. The reference skill indices 36 and 37 are Fire Bolt and Warmth.

The following excerpt replaces the tier baseline in first-map.toml and demonstrates two separate parameters of one stat. It is an advanced single-skill example for an appropriate character and effective skill table, not a way to grant arbitrary usable skills to every class.

Excerpt · replace the tier baseline in first-map.toml
[tiers.tier1]
base_stats = [
  { stat = "item_singleskill", stat_id = 107, layer = 36, value = 1, target = "player", text = "Fire Bolt {signed}" },
  { stat = "item_singleskill", stat_id = 107, layer = 37, value = 2, target = "player", text = "Warmth {signed}" }
]

These remain two entries: (player, 107, 36) and (player, 107, 37). A second bonus at layer 36 would add to the first; it would not increase the layer-37 value. Check the resulting skill behavior on the intended character in game. The example establishes the configuration and parameter relationship; the plugin does not validate every stat consumer or guarantee skill-list refresh.

To choose a layer for another stat, inspect its ItemStatCost definition and the existing property or game feature that supplies its parameter. Parameter layouts are stat-specific; some encode several values. The parser’s 0–65535 range is storage capacity, not a universal “skill ID” interpretation. Leave layer at zero for non-parameterized stats.

Use ranks to check fixed monster baselines

If one tier declares difficulty_rank, every tier must declare a unique rank. The parser checks non-negative, non-decreasing tier monster baseline totals for each stat/layer. An omitted stat counts as zero. Player bonuses, group effects, random traits, density, and rewards are outside that comparison; rank alone does not create difficulty.

Add a monster aura through a trait

Excerpt · recipe-modifiers.toml
[traits.conviction]
weight = 50
text = "Monster Aura: Conviction Lv.{value0}"
monster_aura = { skill_id = 123, level = 10 }

An aura can use a fixed or ranged level from 1–99. A resolved map permits one monster aura. Keep the pool and forced traits from selecting two aura traits together. An aura trait can also contain stats; its first display value is the aura level, followed by its stat values.

The configured aura is applied to eligible monsters in the active map. No player transformation or arbitrary state setting is provided.

07

Choose your map’s monsters.
Add a boss to find.

Give a map its own monster lineup, add a named SuperUnique at a random location, or use both together. You can give different tiers different monsters even when they use the same Level. The monster and boss definitions must already exist in your mod’s game data.

Start with a map you already use

  1. Find the map’s group in your runtime TOML. Open d2rloader/config/native-mapping.toml and find [tiers.<tier>.groups.<group>]. Note its tier name, group name and the Level you want to change.
  2. Add a monster table for that Level. The example below uses tier tier1, group cow_map and Level 39. Replace those three parts with your own names and Level ID. That ID must be included in the group’s levels list.
  3. Choose the settings you need. Keep the pool lines to change ordinary monsters, the superunique line to add a boss, or both. If this monster table already exists, edit it instead of adding a second copy.
Add to your group · example for Level 39
Complete file ↓
[tiers.tier1.groups.cow_map.monsters.39]
nummon = 1
mon = ["zombie1"]
nmon = ["zombie1"]
umon = ["zombie1"]
superunique = { name = "Frozenstein", chance = 100 }

For this map, the example selects zombies in every difficulty and adds Frozenstein somewhere in Level 39 on each new run. It keeps the group’s existing density. Fixed monsters already placed by the map, such as a DS1 boss, remain.

Save the TOML, restart the game and loader, then use your map recipe. To run the same destination again in one game, follow the recrafting procedure. In TCP/IP, use matching plugin builds, TOML and effective game data on Host and Join.

Choose which monsters appear

SettingUse it for
mon = ["zombie1"]The monster candidates in Normal difficulty.
nmon = ["zombie1"]The monster candidates in Nightmare and Hell. Those difficulties also choose random uniques from this population.
umon = ["zombie1"]Normal difficulty’s random-unique candidates. To add a named boss such as Frozenstein, use superunique.
nummon = 1Choose one monster type from the candidates. For a mixture, supply several candidates and increase this number. It counts types, not individual monsters; density controls population density.

Copy names from the Id column of your mod’s MonStats.txt, not the name shown in game. For example, mon = ["zombie1", "skeleton1", "fallen1"] with nummon = 3 offers three types in Normal. Set nmon too if you want that lineup in Nightmare and Hell, and set umon for the Normal random-unique pool.

An array replaces the entire pool. A one-entry array leaves only that candidate; the unused slots are cleared. To keep a pool as defined in Levels.txt, omit its setting. Monster definitions must still be eligible to spawn; listing a disabled or otherwise unsuitable monster does not make it usable.

Change only one slot

Use mon1 = "zombie1" to replace just the first Normal slot while keeping the other slots from the Level’s original data. The equivalent keys are nmon1 and umon1; all three families support slots 1–25. For each pool, choose either its array or its numbered keys. For example, remove mon = [...] before using mon1 in that same table.

"" or -1 clears a slot, and an empty array such as mon = [] clears a whole pool. Keep candidates together from slot 1: the first empty slot ends the usable list, so setting slot 25 after a gap will not add a candidate. Arrays accept up to 25 candidates; nummon accepts 0–255, with the game selecting at most 13 types.

Add a boss without changing the ordinary monsters

Keep the Level’s monster-table heading and just the superunique = { name = "Frozenstein", chance = 100 } line. Leave out mon, nmon, umon and nummon to retain the Level’s original population.

To choose another boss, replace Frozenstein with the exact Superunique value from your mod’s SuperUniques.txt. This is a different kind of name from a MonStats Id. For a custom mapping boss, prepare its TXT definition and dependencies first; you do not need to add a MonPreset/DS1 placement for this additional spawn.

Make the boss guaranteed or occasional

Your choiceWhat to write
Every new mapchance = 100. Leaving out chance also means 100%.
A chance on each new mapchance = 25 for 25%, or chance = 12.3456789 for 12.3456789%.
A very small or near-certain chanceValues can run from 0.0000001 (one in a billion) through 99.9999999, as well as 100.
No additional bossRemove the superunique setting. Do not use chance = 0; it is not accepted.

Use at most seven digits after the decimal point. Write small values as 0.0000001, not 1e-7. Extra decimal digits cause a configuration error instead of being rounded.

Find the boss and run the map again

The boss can be anywhere in that Level’s layout, including an unexplored area far from the entrance or player. Outdoor, maze and preset Levels are supported. Explore the map normally; a boss assigned to an unloaded area appears when that area loads. The Level still needs a valid place for a monster to stand, even at 100%.

Each configured Level gets at most one additional boss per new map. The boss may bring the minions specified in its data. Returning through the portal, revisiting an area or killing the boss does not spawn another. Existing fixed SuperUniques also remain, so use a separate boss definition if you want a distinct mapping encounter.

Recrafting starts another run. If you finish a tiered cow map and use its recipe again, the regenerated map can have its boss again. At 100%, the new run gets another boss; at a lower chance, it gets a fresh chance. Simply leaving and returning to the same run does not retry an unsuccessful roll.

Set the boss’s rewards in your game data

Configure boss rewards in TreasureClassEx, then optionally select a different TC for that boss in each tier using the SuperUnique TC table. superunique chooses the boss and its spawn chance; reward selection is configured separately.

08

Choose the monster.
Replace its TC by tier.

Optionally replace selected Treasure Classes for monsters and SuperUniques inside an active tier map. The same monster can use different TCs in tier1 and tier2. Other monsters, unspecified fields and areas outside that active map keep their usual settings.

The replacement is used by the normal drop rules. It does not add a second reward roll. Define the reward contents, Picks, NoDrop and probabilities in your mod’s TreasureClassEx.txt.

Set up the two optional tables

  1. Choose a tier and target

    Copy the exact tier ID from [tiers.<id>] in your runtime TOML. For monsters, use the Id from your mod’s MonStats. For a SuperUnique, use its Superunique name, such as Bonebreak, rather than its Class or displayed name.

  2. Prepare the reward TCs

    Every TC name you enter must already exist in your mod’s effective TreasureClassEx data. These optional tables select existing TCs; they do not define new TCs or items.

  3. Edit the companion folder

    Keep d2rl-native-mapping.mpq as a folder beside the DLL. Save tab-separated UTF-8 text at the paths below. Do not compress this folder into an MPQ archive or copy the full game tables here.

Paths beside the plugin DLL

Use either table or both. A missing file or a file containing only its header makes no replacements for that table. There is no separate enable switch. Restart the game and loader after editing these files.

Keep the reward contents in TreasureClassEx

A replacement TC can contain item codes and child TCs. If you want to retain an ordinary reward alongside a map item, design that combination in the replacement TC itself; the old reward is not automatically added. Do not put treasureclassex.txt in this companion directory.

For rewards exclusive to a tier, keep these TCs out of ordinary drop trees used elsewhere. The tier rule only controls this replacement; it does not restrict other references to the same TC.

Before starting the game

  • Keep Tier and Id or Superunique in the header. Add only supported TC columns; their order is flexible.
  • Use one row per tier and target in each file. Duplicate headers, duplicate targets, unknown columns and rows with the wrong number of cells are errors. Preserve trailing tabs for empty cells.
  • Save as UTF-8, with or without BOM. Windows and Unix line endings work. Names must match your data; extra spaces are not removed.
  • Malformed tables or an unknown tier prevent the plugin from loading. Unknown monster, SuperUnique or TC names stop preparation of that tier’s map before the existing map is replaced or the Cube recipe runs.
  • Host and Join players need the same plugin version and matching TC rules, alongside matching map configuration and game data. Header order, row order and line endings alone do not change the rules.

Updating an older configuration: remove all [tiers.<id>.progression] tables, including their treasure_class and trigger entries. They are no longer accepted. Choose the targets and difficulty columns in these TXT tables instead; an old all-monster reward is not converted automatically.

For a complete recipe-to-reward setup, follow the three-tier progression example.

One map result, shared by the party.

HOST

Owns gameplay decisions

Chooses the destination and map result. Applies authoritative player and monster stats, density, configured monster pools, SuperUnique spawning, auras, and TC replacements.

JOIN

Mirrors the resolved map

Replays the received route and seed against local configuration and checks the result fingerprint. Displays the map and local player stats; the Host handles TC replacements and configured SuperUnique spawning.

Use the same regeneration-capable plugin build, runtime TOML, and effective mod data on Host and Join. Older DLLs are not compatible with the retirement/result synchronization used by this build. Mismatched routes or resolved results are rejected. The plugin network service is for local/TCP-IP games, not Battle.net.

Effect cleanup follows the individual player's destination. A Host leaving a map does not remove the bonuses of a Join who stays there. A player arriving at a map with no player stats loses the old map's effects. Host snapshot identity and local lifecycle identity are kept separate. Before replacement, the Host also synchronizes the old map’s retirement; Join receives the new result as a new generation so an old result does not restore a retired map.

Check the complete setup and repeat a map

  1. Make the data effective. Save the updated TXT in your mod’s active data tree. For a loose TXT workflow, regenerate compiled data through your normal -mod <mod-name> -txt launch flow. A packaged or precompiled workflow must include the regenerated data in the package actually loaded.

Field reference.

Names are configuration identifiers, not file paths. Numeric IDs refer to effective mod data. Integer ranges use { min, max, step }: step must be positive, min must not exceed max, and the interval must divide evenly by step.

Location / fieldsDefault and accepted values
Rootconfig_version = 1; enabled = true; random_salt = "native-mapping" (1–256 bytes). The salt influences map-result selection, not the retained game/Act terrain seed or item generation seeds.
cube_routes.<id>inputs: 1–255 item codes, each 1–4 printable non-space bytes. tier: existing tier ID. modifiers: ordered IDs, default empty. Duplicate exact multisets, including compiled aliases, are rejected.
tiers.<id>base_stats: fixed values only, default empty. trait_count: { min, max }, defaults to zero. At least one group is required; every tier must be referenced by a route.
difficulty_rankOptional unsigned 32-bit rank. If used, required and unique on every tier. Ranked monster baseline totals must be non-negative and non-decreasing.
groups.<id>levels: unique IDs, 0–255, non-empty. entrances: non-empty { level, weight } entries, unique and inside levels. The numeric range alone does not establish a usable destination.
Group / entrance weightPositive unsigned 32-bit integer, default 1. Relative to all candidates in that group-selection or entrance-selection pool; prior map use does not remove candidates.
Group densityPositive signed 64-bit integer or range; default 100. A percentage of original density. The parser has no 1000% ceiling; the native population path caps the resulting MonDen at 10,000.
groups.<id>.monsters.<level>Optional per-Level policy. The Level must be in this group’s levels. Omitted pool fields inherit the original data; different tiers/groups can define different policies.
Monster mon, nmon, umonWhole-pool arrays, at most 25 entries; clear unused tails. Alternatively use numbered keys 1–25 for individual slots. Do not mix both forms for one pool. Values are MonStats Id strings or valid compiled indices 0–32767; "" or -1 clears a slot. The first empty slot ends the native pool. See difficulty semantics.
Monster nummonOptional integer, 0–255; native selection cap 13 types. Omission inherits the Level value. This is a type count, independent of density.
Monster superuniqueOptional { name, chance }. Name must resolve to a SuperUniques Superunique key. Omission disables the additional spawn; pool overrides are not required.
superunique.chancePercent, 0.0000001–100 inclusive; default 100. Up to seven decimal places, no exponent notation or zero. One decision and at most one boss per configured Level and generation. See placement and regeneration.
Group effect fieldsbase_stats allows fixed or ranged values. forced_traits is a list of distinct existing trait IDs that are selected first. trait_pool supplies the remaining random candidates. trait_count overrides the tier when present and counts forced plus random traits together.
traits.<id>weight defaults to 1 and is positive. text defaults to the trait ID. Requires stats, monster_aura, or both.
A stat entrystat_id: required, 0–65535. stat: optional name. layer: 0–65535, default 0. target: player or monster, default player. value: signed 32-bit integer or range, default 0; native encoding limits also apply.
Stat display / sharingroll_group shares an identical range within one array. text defaults to empty for baseline entries. Optional color is parsed but not emitted as a line color.
monster_auraskill_id: required, 1–65535. skill: optional name. level: integer or range, 1–99, default 1. One aura per resolved map.
modifiers.<id>forced_traits, trait_pool, trait_count. Pool mode defaults to extend; explicit trait_pool_mode requires an explicit pool. Count conflicts in a route are rejected.
Optional TC tablesCompanion monstats.txt and superuniques.txt: Tier + target key + selected difficulty/category columns. See columns and cell values. No TOML reward table is required.
hudenabled=true; density_text="Monster Density: {value}%"; overflow_text="+{value} more"; max_lines=16 (2–256). tier_color, density_color, and trait_color do not set visible per-line colors in this builder.

Identifiers accept letters, digits, underscores, hyphens and dots, up to 96 bytes. Quote literal dotted keys in TOML. Display text is single-line and limited to 256 bytes. A resolved map supports up to 256 stat entries before coalescing; the active map capacity is 64, with retired slots reused during replacement. These bounds do not define how many monsters a Level can contain.
